# UI transport

The Pulse Factory UI is one React and TypeScript bundle (`apps/ui`, ADR-0013). It reaches the
controller's network API (`api.md`, ADR-0012) only through the **transport interface** below. The
UI never opens a TLS connection, never sees the device token and never keeps it. This file is
version 1 of the interface and of the bridge protocol.

Two things implement the interface:

- **The Mac app** (`r1.s2.w4`): the Tauri shell's Rust side holds the token in the Keychain, makes
  the pinned TLS call and exposes the six methods as Tauri commands with the names and shapes
  below.
- **The test bridge**, `pf-client-bridge` (`crates/pf-client`; `scripts/demo/ui-bridge/README.md`): the
  `desktop-bridge` fake (`SPINE.md`, Fakes), now with the real pinned client behind it. It stands in
  for the Tauri shell's Rust side where the Mac app cannot run, such as headless Chromium on
  draco-desk. It is for `scripts/demo/ui-pair.sh` (d12) and tests only. The Mac app does not use it.
  It was a Node script until `r1.s2.w4`. After that item the fake covers only the Tauri `invoke` glue
  and the Keychain.

## The interface

`apps/ui/src/transport/types.ts`. The types come from `@pulse-factory/api-client`
(`apps/api-client/src/gen/`, generated by `ts-rs`).

```ts
export type TransportErrorKind =
  | 'unreachable'   // no HTTP answer: refused, reset, timed out, name not found
  | 'unauthorized'  // 401 on a token route: a revoked, idle or unknown device
  | 'code_refused'  // 401 on /v1/pair: a used, expired, replaced or malformed code
  | 'key_changed'   // the server key is not the pinned one; nothing was sent
  | 'forbidden'     // 403
  | 'refused'       // 422: the handler's refusal, its text kept
  | 'rate_limited'  // 429
  | 'bad_request'   // 400 or 413
  | 'server';       // 5xx, or an answer that is not the documented JSON
export class TransportError extends Error { readonly kind: TransportErrorKind }
export interface PairedServer { address: string; device: DeviceRecord }
export interface Transport {
  paired(): Promise<PairedServer | null>;           // no network call
  pair(code: string, deviceName: string): Promise<PairedServer>;
  status(): Promise<ApiStatus>;
  projectList(): Promise<ProjectList>;
  projectAdd(args: ProjectAddArgs): Promise<ProjectChanged>;
  forget(): Promise<void>;                          // drops the token on this device only
}
```

- **No method takes or returns the device token.** The token lives on the native side.
- `forget()` removes this device's token and pin. The server still lists the device until the
  operator runs `pulse-factory device revoke <id>`, so the UI tells the operator that command, with
  the device's ID.
- The message of a `key_changed` error is exactly `server key changed: re-pair`.
- `projectAdd` carries a `command_id`. A retry of the same submit reuses it (`api.md`, A7).

## Error kinds

Each kind comes from one API answer or one local condition. The text of `refused`, `rate_limited`,
`forbidden`, `bad_request` and `server` is the server's own `{"error": "<text>"}`, cut to 300
characters, or `the server answered <status>` when the answer has none or the text would hold a
secret.

| Kind | Comes from |
|---|---|
| `unreachable` | No HTTP answer: connection refused, reset, timed out, name not found, a TLS failure before the pin check. |
| `unauthorized` | 401 on a route that needs a token (`GET /v1/status`, `POST /v1/verbs/<verb>`). Also a call on a device that holds no token. |
| `code_refused` | 401 on `POST /v1/pair`. Also a code that does not decode (no network call is made). |
| `key_changed` | The server's key is not the pinned one. The check is before any byte is written. |
| `forbidden` | 403: a verb that is not on the allowlist. |
| `refused` | 422: the controller refused the command, or the device name is invalid. |
| `rate_limited` | 429 (`r1.s2.w5`). |
| `bad_request` | 400 or 413. Also a request the bridge cannot form. |
| `server` | 500 or any other status, or a 200 that is not JSON. |

### What the UI does with each kind

| Kind | Screen |
|---|---|
| `unreachable` | 3c banner "Not connected to <address>"; retries `status()` after 4, 8, 16, 32 and then every 60 seconds. This is the only kind that sets a timer: no request reached the server. |
| `unauthorized` | 3c banner "This device is no longer paired with <address>." and "Pair again". No timer. |
| `key_changed` | 3c banner `server key changed: re-pair` and "Pair again". No timer. |
| `rate_limited` | 3c banner with the server's text and "Retry now". No timer. |
| `forbidden`, `bad_request`, `server`, `refused` | One error line on the page with the text and "Retry now". The page keeps its last data. No timer. |
| `code_refused` | On 3a: the code is not accepted, ask for a new one. The form stays. |

### When the UI calls

On start, on opening a page, after an action, and on "Retry now". **While connected no timer,
interval or focus handler makes a call** (planning audit C15: the controller's ledger is local and
unbounded). After an HTTP refusal the UI never retries by itself.

## The bridge protocol

HTTP on `127.0.0.1`, on the same origin as the bundle. The bridge serves the bundle's files at `/`
and these routes:

| Route | Body | Result (inside `{"ok": true, "result": …}`) |
|---|---|---|
| `GET /bridge/paired` | none | `PairedServer`, or `null` when no server is paired. No network call. |
| `POST /bridge/pair` | `{"code": "<pf1-…>", "device_name": "<name>"}` | `PairedServer`. The bridge checks the pin, then calls `POST /v1/pair`, and keeps the token. |
| `POST /bridge/status` | `{}` | `ApiStatus` (`GET /v1/status`). |
| `POST /bridge/verbs/<verb>` | the verb's JSON arguments | the verb's JSON answer (`POST /v1/verbs/<verb>`). `<verb>` is `[a-z][a-z_]*`; anything else is `bad_request`. |
| `POST /bridge/forget` | `{}` | `null`. Removes the device file. |

**Every bridge answer is HTTP 200** with `{"ok": true, "result": …}` or `{"ok": false, "error":
{"kind": "<TransportErrorKind>", "message": "<text>"}}`. No answer holds the device token or the
code.

`pf-client-bridge` serves this protocol, and the Mac app's Tauri commands carry the same names and
shapes (next section).

## The Tauri commands

`apps/desktop/src-tauri` registers six commands. Each is one method of the interface, in snake case,
and each calls `pf-client`'s `Transport<KeychainStore>`. `apps/ui/src/transport/tauri.ts` calls them
with `invoke` from `@tauri-apps/api/core`, which turns a JavaScript argument name in camel case into
the Rust one in snake case.

| Command | `invoke` arguments | Returns |
|---|---|---|
| `paired` | none | `PairedServer`, or `null`. No network call. |
| `pair` | `{code, deviceName}` | `PairedServer`. The token goes to the Keychain. |
| `status` | none | `ApiStatus`. |
| `project_list` | none | `ProjectList`. |
| `project_add` | `{args}`: a `ProjectAddArgs` | `ProjectChanged`. |
| `forget` | none | nothing. Deletes the Keychain item and the pairing file. |

A command returns the wire type itself, with no `{"ok": …}` envelope. A command that fails rejects
with `{"kind": "<TransportErrorKind>", "message": "<text>"}`, the shape of the `error` member of a
bridge answer. The UI turns a rejection into a `TransportError` of that kind. A rejection of any other
shape, or with a kind that is not one of the nine, becomes a `server` error. No command takes or
returns the device token. The webview's content security policy allows the bundle's own assets and
Tauri's IPC only, so the webview opens no network connection.

### What the bridge does

- **The pin check** (`api.md`, "The pin check"). `pair` decodes the code (`pf1-` and lower-case
  base32 of version, 10-byte secret, 32-byte SPKI hash and the address), connects to the code's
  address with TLS 1.3 and no chain check, takes the peer's SubjectPublicKeyInfo, compares its
  SHA-256 with the hash in the code, and only then sends `POST /v1/pair`. A mismatch destroys the
  socket **before any byte is written** and answers `key_changed`. Every later call pins the same
  hash the same way, so a key that changes after pairing fails closed too.
  - The SPKI comes from the DER of the peer's end-entity certificate. `pf-client` reads it in Rust
    (`crates/pf-client/src/pin.rs`) and hashes the whole SubjectPublicKeyInfo element: for an ECDSA
    P-256 key that is 91 bytes, not the bare 65-byte point. The verifier also checks the handshake
    signature against the certificate's key, so the peer must hold the pinned key.
- **The token.** The token, the pin and the address are in `<state>/device.json`, mode 0600, and
  nowhere else (it also keeps the device record, which `paired` returns). The bridge never writes the
  token or the code to stdout, stderr or an answer. It prints one line, `listening
  http://127.0.0.1:<port>`.
- **Who may call it.** The bridge refuses (HTTP 403, plain text) a request whose `Host` is not its own
  `127.0.0.1:<port>`, whose `Origin` is not its own origin, or a `POST` that is not
  `application/json`. A page on another origin cannot call it, and a DNS rebinding cannot either.
- **The files.** `pf-client-bridge --ui <dir> --state <dir>` serves `<dir>` and nothing outside it (a
  path with `..` is refused, and so is a link that leads outside), with a content security policy that
  allows the bundle's own origin only.
