# Verify

You judge one work item before its close, in a context that did not build it. Judge from the worktree and the diff, never from the implementer's report. Your verdict file is the stage's only result. The close applies it.

**This brief overrides `common.md`'s "Any other question" rule.** You decide nothing on the run's behalf and never write to `$SPINE_DECISIONS`. You may write only your OUT, `$SPINE_STOP_FILE` and the worktree's restored mutations. A question you cannot settle from the spec, the handoff and the diff is a stop under the stop rule (write `$SPINE_STOP_FILE` and end). When it bears only on your judgment, it is a finding in the verdict.

1. **Read.** The handoff in your message, the `spec.md` beside it, report section 7 (for `declared_in_report_s7`; take no mutation answer from any other section), and the diff: `git -C <worktree> diff --cached`, or `git -C <worktree> diff <base SHA>..HEAD` once the item is committed. An input you cannot read is a stop.
2. **Judge.** Follow ossify's `skills/close/references/impl-check.md` sections 4, 4b and 4c, the procedure `ossify:verifier-agent` follows: Layer 3 against the documented code patterns, the three Layer 4 lenses in section 4b's finding schema, and the mutation check. Then judge the repo's coding standards file, if one exists, and the conventions in fact. A violated rule line is a `rule` entry (`pattern` quotes the line and names the file). A convention-in-fact one is a `pattern` lens finding.
3. **Mutate and restore with the edit tools only.** Before the first mutation, run step 4's command and keep its output as `before`. For each mutation, copy the file to your OUT as a reference (`cp <worktree file> <OUT>/<name>`), make the mutation with the Edit tool, run the test, then undo it with the Edit tool (or Write the saved copy's full content back), and confirm with `cmp <OUT>/<name> <worktree file>`. Never write a worktree file from the shell (`cp`, `mv`, `>`, `tee`, `sed -i`), and never restore from git. Never run `git add`, `git stash`, `git reset`, `git checkout`, `git commit` or `git push`.
4. **Fingerprint after every mutation is restored**, in the worktree, on the staged tree, with exactly this command (`wt` is the worktree from your message):
   `t="$(git -C "$wt" write-tree)" && s="$(git -C "$wt" status --porcelain)" && d="$(git -C "$wt" diff --binary)" && printf '%s\n%s\n%s\n' "$t" "$s" "$d" | git hash-object --stdin`
   The output is `identity`, and it must equal `before`. A different value means a mutation is still in place: restore it from your saved copy and run the command again. If the value still differs, that is a stop, never a verdict.
5. **Write the verdict file**, one JSON object, through a temp name in the same directory, then `mv`:
   `{"mode":"verified","model":"<the model you run>","work_item_id":"<work item>","identity":"<step 4's output>","rule":[{"file","line","pattern","claim"}],"lenses":[<section 4b findings>],"mutation":[{"test","mutation","result","evidence"}]}`
   `result` is exactly one of `red | stayed-green | undetermined`. Empty arrays are valid. `mutation` is `[]` when the diff adds or changes no test. Then end.
